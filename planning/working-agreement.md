# Working Agreement

Use this short protocol for every future body of work so the project does not drift from its purpose.

## Before starting

1. Name the active stage from [stages-and-gates.md](stages-and-gates.md).
2. Read the [product compass](../docs/product/product-compass.md).
3. State the current user problem in one sentence.
4. Identify the confirmed decision that authorizes the work.
5. Check whether the work crosses a decision gate. If it does, stop for confirmation.

## While working

- Keep one obvious action per daily state.
- Do not add manual status, actual-time, progress, tagging, or organization work to the normal loop.
- Use the Q4 representative scenarios: normal Monday, bundled Wednesday, unfinished collision, conditional Friday, light week, and quarter retro.
- Preserve user history and original plan intent.
- Record meaningful changes to confirmed behavior in the decision log.
- Prefer removing a choice over explaining it.

## Before declaring a stage complete

- Verify every required deliverable in the stage gate.
- Check links and document consistency.
- List chosen and rejected alternatives.
- Identify unresolved assumptions honestly.
- Update the decision log and the current-stage marker.
- Ask for explicit confirmation when the gate requires it.

## Before implementing any feature (after the implementation gate)

Answer all five:

1. What current learner problem does this solve?
2. Which confirmed journey and screen does it support?
3. What information can be inferred instead of entered?
4. What happens on a busy, low-energy, or interrupted day?
5. Does the feature make the app easier than a timer plus notes?

“We may need it later” is not sufficient justification.
